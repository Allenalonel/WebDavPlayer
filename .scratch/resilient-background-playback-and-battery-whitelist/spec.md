# Spec: 弹性后台播放保活、延迟降级、双硬件锁与厂商电池白名单 (Resilient Background Playback, Deferred Demotion, Dual Hardware Locks & OEM Battery Whitelist)

Status: ready-for-agent

## Problem Statement

作为 WebDAV 在线流式音乐播放器的用户，在使用手机锁屏播放音频时，经常遇到播放数分钟后声音戛然而止的问题；重新点亮屏幕后，发现播放器卡死在历史进度点（例如 04:36），总时长显示为 00:00，界面处于假死或无法即刻播放的状态。

通过对系统底层的排查，该现象是由于国产定制系统（如小米 MIUI / HyperOS）激进的“锁屏清理（LockScreenClean）”机制在后台直接强制杀除了应用进程（`force-stop`）。进一步溯源发现，应用本身的后台播放与保活架构存在多重系统契约与设计缺陷：
1. **前台服务过早降级**：播放暂停时，应用立即解除了前台服务身份，退化为普通后台服务，并在数分钟内被系统认定为“闲置（app idle）”而强行停止；
2. **后台提权非法阻断**：暂停降级后再尝试恢复播放时，因处于后台而触发系统的后台启动限制（`Background start not allowed` 与 `startForeground() not allowed due to bg restriction`），导致前台服务再也无法恢复，服务甚至完全丢失；
3. **缺少硬件级休眠锁**：WebDavPlayer 依赖纯在线流式传输（无磁盘持久化缓存），手机息屏后系统 CPU 进入深度睡眠（Deep Sleep），Wi-Fi 芯片进入节能降频，缺少 CPU 唤醒锁与 Wi-Fi 锁导致网络流式读取直接挂死超时；
4. **单进程内存堆积**：由于单进程内 UI 位图和视图缓存驻留，后台内存占用偏大（130MB+），加剧了触发系统 Low Memory Killer (LMK) 的风险；
5. **缺少厂商防杀引导**：用户未开启系统的“忽略电池优化”与 MIUI 的“无限制省电/自启动”，使应用完全暴露在厂商系统的白名单查杀策略之下。

用户期望无论手机锁屏多久，后台流式播放都能坚如磐石；暂停片刻后通过耳机线控或通知栏能即刻零延迟恢复播放；即使遇到系统强杀，冷启动也能明确感知并引导用户一键配置后台白名单。

## Solution

对标椒盐音乐（Salt Player）等业界标杆独立播放器的后台设计经验，在保持轻量单进程模型的前提下，打造一套完整的后台弹性保活与硬件防护体系：

1. **单进程内部架构与生命周期治理**：
   - 在应用处于合法前台窗口期（`onStart`）主动预热并绑定媒体播放服务，杜绝后台非法启动异常；
   - 保证前台身份单向连续性，暂停时不注销前台服务，状态切换仅通过通知管理器就地更新按键状态，杜绝后台重新提权异常；
   - 实现退后台内存自洁机制（`onTrimMemory`），应用切后台或息屏时立即清空大图位图内存缓存，将后台常驻内存压降 60%（降至约 50MB），消除 LMK 查杀风险；
   - 强化服务粘性（`START_STICKY`），并完善多任务划除时的任务守护，保障划掉卡片时后台音乐不中断。
2. **15 分钟延迟前台服务降级（Deferred Foreground Demotion）**：
   - 用户暂停播放后，前台服务维持活跃并启动 15 分钟倒计时；
   - 15 分钟内用户点击恢复播放，瞬间取消倒计时并零延迟无缝恢复；
   - 15 分钟超时未操作，优雅降级释放前台身份，兼顾电量节约。
3. **流式双硬件锁守护（Dual Streaming Hardware Locks）**：
   - 播放与流式缓冲时，底层播放器内核自动持有 CPU 唤醒锁（WakeLock），网络数据源层持有 Wi-Fi 高性能锁（WifiLock），杜绝息屏降频断流；
   - 暂停与空闲时，立即释放两把硬件锁，允许手机锁屏深度睡眠，绝不产生多余电量开销。
4. **厂商防杀感知与白名单常驻横幅（OEM Kill Detection & Whitelist Banner）**：
   - 持久化会话记录退出健康度标记，冷启动时自动识别上次是否在播放中被系统强杀；
   - 全屏播放器顶部实时检测电池优化白名单状态，未开启时常驻展示美观的提示卡片，支持一键调起系统电池优化弹窗与厂商（MIUI/HyperOS 等）自启动及无限制省电模式设置页。

## User Stories

1. 作为移动端音乐收听者，当我将手机息屏放入口袋后，我希望 WebDAV 远程音频流能够持续顺畅播放数小时，不会因系统锁屏清理或 CPU 休眠而中途突发卡死断流。
2. 作为使用蓝牙耳机的用户，当我在听歌途中临时暂停对话（15 分钟以内），对话结束后按下耳机播放键时，我希望音乐能够瞬间零延迟恢复播放，通知栏和播放服务不发生任何重启或丢状态。
3. 作为关注手机电池续航的用户，当我暂停音乐超过 15 分钟且忘记关闭播放器时，我希望播放器能够自动优雅地退出前台服务身份并释放硬件锁，避免无谓消耗手机电量。
4. 作为纯在线流式音频听众，当手机处于锁屏状态且正在从远程 WebDAV 服务器缓冲高码率无损音频时，我希望 Wi-Fi 芯片持续处于高性能无休眠状态，网络传输平稳高速，不因网卡降频节能而发生缓冲饥饿。
5. 作为纯在线流式音频听众，当我点击暂停按钮时，我希望 Wi-Fi 高性能锁和 CPU 唤醒锁能够被立即释放，使手机硬件能够正常进入低功耗待机模式。
6. 作为从桌面冷启动点开播放器的用户，当应用在前台初始化时，我希望播放核心服务能够在系统允许的合法时间窗口内完成预热和绑定，彻底杜绝发生 `Background start not allowed` 系统崩溃。
7. 作为经常在多应用间切换的多任务重度用户，当我将播放器切入后台或锁屏时，我希望应用能够主动清空大图位图内存占用，使常驻内存降低到 50MB 左右，大大降低被系统 Low Memory Killer 杀除的几率。
8. 作为多任务卡片习惯清理者，当我在手机任务列表向上划掉播放器的界面卡片时，如果当前正在播放音乐，我希望音乐继续稳定播放，前台通知栏不消失，避免应用被误自杀。
9. 作为小米（MIUI / HyperOS）手机用户，当我因未开启白名单导致上次锁屏播放被系统强制清理后，下次打开播放器时我希望能看到友好的被杀感知提示，清楚了解停止播放的根本原因。
10. 作为尚未给播放器配置电池白名单的用户，当我在全屏播放器界面浏览时，我希望在顶部看到一条常驻的温馨提示横幅，明确告知我锁屏可能面临的断流风险。
11. 作为希望快速完成设置的用户，当我点击全屏播放器顶部的优化横幅时，我希望系统直接弹出“忽略电池优化”授权对话框，一键点击即可完成标准加入白名单。
12. 作为小米手机用户，当点击优化引导时，我希望能够一键直接跳转至该应用的小米系统配置页，引导我开启“自启动”并将省电策略设为“无限制”，从源头彻底消灭 MIUI 的 `LockScreenClean`。
13. 作为已完成权限配置的用户，当我已经授权忽略电池优化后，我希望全屏播放器顶部的横幅能够自动平滑隐去，还给界面极致纯净的沉浸体验。
14. 作为收听 CUE 虚拟分轨音频的用户，在手机长时间锁屏期间，我希望虚拟分轨能够在双硬件锁的保护下平滑自然跨轨推进，通知栏元数据同步更新。
15. 作为收听长篇评书或相声的用户，当一集在锁屏状态下播放完毕且处于列表循环时，我希望会话层能够顺利拉起下一集流式数据源，前台服务不中断。
16. 作为遭遇临时网络抖动的用户，当后台流式传输因瞬时断开触发重试时，我希望双硬件锁能够维持连接环境稳定，配合数据源退避机制顺利自愈，不因系统误杀而提前退出。
17. 作为应用架构维护者，当我编写单元测试验证延迟降级状态机时，我希望通过虚拟时间调度器快速推进 15 分钟，能够精准断言前台服务在超时后被降级释放。
18. 作为应用架构维护者，当我编写测试验证硬件锁管理时，我希望能够在播放和缓冲时断言锁处于持锁状态，在暂停和停止时断言锁已安全释放。
19. 作为应用架构维护者，在实现后台保活强化时，我希望整个解决方案完全收敛在单进程内部，无需引入复杂的 AIDL 跨进程通信或破坏现有的 Room/DataStore 单点持久化模型。

## Implementation Decisions

### 1. 宿主服务生命周期强化 (Service-Centric Lifecycle Hardening)
- **前台窗口主动预热**：
  在应用顶层生命周期的前台可见回调中，主动调用服务启动与绑定契约，确保所有前台服务提升和绑定均在系统合法的窗口期内完成。
- **服务粘性与防误划逻辑**：
  - 媒体播放服务在启动命令处理中统一返回 `START_STICKY` 标志；
  - 覆盖任务移除回调（`onTaskRemoved`）：若当前状态处于回放中，或处于 15 分钟延迟降级窗口内，坚决不主动终止服务进程；仅在明确超时或用户显式请求退出时才执行销毁。
- **退后台内存修剪 (TrimMemory Guard)**：
  在应用级与 Activity 级组件回调中接入系统内存告警监听，当告警等级达到或超过 `TRIM_MEMORY_UI_HIDDEN` 时，同步调用缩略图内存缓存的清空接口（`ThumbnailMemoryCache.clear()`），并触发轻量对象回收，确保后台态常驻内存最小化。

### 2. 15 分钟延迟前台降级状态机 (Deferred Foreground Demotion State Machine)
- **延迟降级调度器**：
  在播放会话宿主内部维护专职的延迟降级倒计时协程作业（`Job`），默认超时常量设为 15 分钟（`15 * 60 * 1000L`）。
- **状态转移规则**：
  - 引擎状态转为 `PlaybackState.Playing` 或 `PlaybackState.Buffering` 时：若存在挂起的降级作业，立即取消该作业；若前台未提升则执行前台服务安全提升；
  - 引擎状态转为 `PlaybackState.Paused` 时：不执行 `stopForeground`；在当前前台状态下通过通知管理器仅刷新通知栏视图（更新为暂停按键与最新进度），同时启动 15 分钟延迟作业；
  - 延迟作业自然超时触发时：在协程中调用 `service.stopForeground(STOP_FOREGROUND_DETACH)`，将前台通知转换为可滑除的常规通知，退出高优先级前台身份；
  - 引擎状态转为 `PlaybackState.Idle` 或 `PlaybackState.Ended` 且无后续队列时：取消延迟作业，立即脱离前台服务并移除通知。

### 3. 流式双硬件锁管理器 (Streaming Hardware Lock Manager)
- **架构接缝与接口设计**：
  抽象出专职的硬件锁管理抽象（`StreamingHardwareLockManager`），封装底层系统的 `PowerManager.WakeLock` 与 `WifiManager.WifiLock`。
- **ExoPlayer 内核唤醒配置**：
  在创建底层播放器实例时显式开启网络唤醒模式（`.setWakeMode(C.WAKE_MODE_NETWORK)`），交由播放内核在音频流水线运转时自动持有 `PARTIAL_WAKE_LOCK`。
- **Wi-Fi 高性能锁装配**：
  数据源适配层持有 `WifiManager.WifiLock`（采用 `WIFI_MODE_FULL_HIGH_PERF`，自定义标示为 `"WebDavPlayer:StreamingWifiLock"`）。
- **联动释放语义**：
  - 随播放引擎的活跃回放状态（`Playing` / `Buffering`）同步获取 Wi-Fi 锁；
  - 随暂停（`Paused`）、停止（`Idle` / `Ended`）或释放（`release`）状态立即释放 Wi-Fi 锁，确保设备锁屏能正常进入深层节电休眠。

### 4. 厂商查杀感知与电池优化横幅 (OEM Kill Detection & Whitelist Integration)
- **会话持久化健康状态追踪**：
  在播放会话数据模型（`PlaybackSessionData`）与持久化存储接缝中增加退出标志 `cleanExit: Boolean`。正常暂停、停止或正常切歌退出时写入 `true`；开始播放或流式推进时写回 `false`。
- **冷启动被杀研判**：
  应用冷启动恢复会话时，若检测到 `cleanExit == false` 且记录的历史状态属于播放中，即可确认上次进程被系统强杀（如 MIUI `LockScreenClean`），并在播放会话状态流中置位 `wasKilledBySystem = true`。
- **白名单状态检测与交互横幅**：
  - 封装系统电源管理服务检测契约：`powerManager.isIgnoringBatteryOptimizations(packageName)`；
  - 在全屏大播放器视图（`FullPlayerSheet`）的顶栏下方嵌入常驻横幅组件；当且仅当未开启白名单时展示卡片提示；支持用户点击跳转或本次会话临时收起；
  - 授权点击交互适配：
    1. 优先调用系统标准意图 `Settings.ACTION_REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` 触发原生白名单授权弹窗；
    2. 检测系统品牌（如包含 Xiaomi / Redmi 等特征），提供针对 MIUI / HyperOS 的应用设置页跳转意图与图文步骤指引（引导开启自启动与神隐模式无限制）。

## Testing Decisions

### 什么是好的测试 (What Makes a Good Test)
- **只测试外部可观测的行为与状态转变，不耦合任何内部私有变量**：
  例如，断言“在调用暂停后，前台服务标记在 14 分钟时依然有效，推进至 15 分钟后前台标记变为 false 且脱离通知”，而不是测试具体的定时器私有变量名；
- **接口即测试表面**：
  利用现有的 `PlaybackSessionHostTest`、`MusicPlayerAppSessionTest` 以及高层 Fake 引擎进行驱动，测试覆盖生产环境真实运行的调用路径。

### 被测模块与重点场景 (Modules to be Tested)
1. **`PlaybackSessionHostTest`**：
   - 验证延迟前台降级状态机：暂停触发 15 分钟倒计时、倒计时中途恢复播放取消计时器、倒计时超时执行脱离前台；
   - 验证双硬件锁的获取与释放生命周期：播放/缓冲持锁、暂停/停止立即释锁；
   - 验证 `onTaskRemoved` 在播放态与暂停宽容态下的守护逻辑；
   - 验证前台启动与状态更新时的幂等性。
2. **`MusicPlayerAppSessionTest`**：
   - 验证冷启动时根据 `cleanExit` 标志准确推导 `wasKilledBySystem` 状态流；
   - 验证会话保存时能够正确记录播放健康状态。
3. **`ThumbnailMemoryCacheTest`**：
   - 验证在触发 `onTrimMemory` 模拟信号时，位图缓存被全量清理。
4. **`FullPlayerPresentationTest`**：
   - 验证在未加入电池优化白名单时，全屏播放器正确呈现提示横幅；
   - 验证加入白名单后，横幅自动隐去；
   - 验证横幅点击触发意图分发。

### 代码库现有测试先例 (Prior Art)
- `PlaybackSessionHostTest.kt`：已有一套针对前台服务提升和状态分发的 Robolectric / 纯 JVM 测试基座；
- `ProcessRestartSimulationTest.kt`：已有一套模拟进程被杀死后通过持久化数据还原会话的端到端测试；
- `ThumbnailMemoryCacheTest.kt`：现有的位图缓存存取测试；
- `FullPlayerPresentationTest.kt`：现有的全屏播放器 Compose 状态渲染测试。

## Out of Scope

- **多进程架构重构**：本次坚守单进程模型，不引入 `:playback` 独立进程，不重写 AIDL / IPC 数据通信链路；
- **第三方非合规保活套件**：不接入任何利用 Android 系统漏洞的“双进程拉活”、“像素悬浮窗”等非合规黑科技手段，严格遵循 Google 与厂商推荐的系统级 API；
- **本地持久化音频切片缓存**：严格遵循 ADR-0002 纯在线流式规范，不引入持久化磁盘音频下载或分段缓存。
